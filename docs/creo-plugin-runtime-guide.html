CreoToolkit · 运行原理图解

把 .NET 装进 Creo 里跑,
再让 Creo 反过来听 .NET 的话

Creo 是 C++ 世界,不认识 .NET。我们的插件要在 Creo 里跑起来,得把 .NET 运行时"手动"塞进去, 再让托管代码回头调 Creo 的 API。这一页把这条链路讲清楚,顺便回答一个高频问题—— 我们的测试是怎么"告诉 Creo 该跑哪条命令"的。

§ 1 Big picture

01一句话总览

整条链路的精髓其实是一个 "回旋"——从 native 出发,拉起 .NET runtime,让 managed 代码接管命令注册, 然后 managed 里的 P/Invoke 又反过来调回同一个 native dll,再由它转发给 Creo。

出发点 · Creo(C++)

Creo 启动
↓ LoadLibrary
NativeHost.dll
手工拉起 CLR

终点 · .NET 命令层

Bootstrap.InitializeApp
↓ 注册命令
用户/测试 触发

触发链路上的信息传递,靠一张最朴素的 "纸条"——Windows 环境变量。 测试或者脚本在启动 Creo 之前 把命令名写在纸条上,插件启动后自己去读,读到就跑,读不到就静静等用户点菜单。

为什么这么设计? 环境变量是操作系统级基础设施,Creo 子进程会继承父进程的环境变量, 不需要额外的 pipe / RPC / 网络通道。开发/测试/生产三个模式共用同一段命令实现代码, 变的只是"要不要在纸条上写字"。

§ 3 Trigger

03命令怎么被触发:便条机制

测试进程和 Creo 里的插件不需要"实时对话"——一张写好命令名的纸条 + 一份写结果的小本本,就够了。

类比

咖啡机的定时功能

Harness 出门前在便条上写:"进屋后请去做 A 事,做完把每一步记在小本本上"。 Creo 里的插件一启动就去读便条,照着做,结果全部写进小本本。Harness 每秒偷看一次小本本, 看见"我干完了"那句就把整个本子抄回来给测试代码断言。

这个链路在代码里是这么四行接力的:

端 A · 测试进程写便条 
// tests\CreoToolkit.RealCreoIntegration\CreoTestHarness.cs
["CTK_APP_RUN_COMMAND"] = commandName,
//   ↑ 就在这里写:要跑哪条命令
端 B · Creo 里的插件读便条并触发 
// src\CreoToolkit.Diagnostics\DiagnosticsStartupOptions.cs
var runCommand = NullIfWhiteSpace(readEnvironment(CtkEnv.AppRunCommand));
// src\CreoToolkit.Diagnostics\StartupDiagnostics.cs
if (options.DiagnosticCommand is { } command)   //  ← 便条有字才跑
{
    var rc = appHost.RunCommandForDiagnostics(command);
    log($"InitializeApp: diagnostic command '{command}' rc={rc}.");
}
// 便条没字 → 跳过整段 → 命令注册好,静静等用户点菜单
端 A · 测试进程偷看小本本 
// tests\CreoToolkit.RealCreoIntegration\CreoTestHarness.cs
|| content.Contains($"diagnostic command '{commandName}' rc=", ...)
//   ↑ 看见 "rc=" 就知道插件干完了,可以停止轮询
端 B · 命令分发(按名找命令) 
// src\CreoToolkit.App\CommandDispatchRuntime.cs
internal int InvokeByName(string name)
{
    foreach (var command in GetCommands())
    {
        if (string.Equals(command.Name, name, StringComparison.Ordinal))
            return Dispatch(command.Token);  // ← 与用户点击进入同一 callback
    }
    return 2;  // 找不到命令名
}
为什么开发模式不受影响? DiagnosticsStartupOptions 对 CTK_APP_RUN_COMMAND 的判空就是分岔口: 环境变量有值 → 自动跑;环境变量为空 → 命令注册好后闭嘴,等用户手动。没有 任何 if (isTestMode) 之类的分支——同一段代码,两种入口。

§ 4 Loading order

048 步加载顺序图解

从 Creo 双击启动到我们插件的命令注册完成,系统里其实按下面这个精确顺序发生了 8 件事。

1

Creo 主程序启动

By: 操作系统

Windows 启动 parametric.exe,Creo 主进程跑起来。此时它还不知道我们插件的存在。

2

Creo 读 protk.dat,找到我们的插件

By: Creo

launcher 在选定的 Creo 工作目录写入 protk.dat——这是本次会话的插件注册文件,里面写了 NativeHost 的绝对路径和当前 app 的文本资源目录。仓库中的 protk.host.dat 只是占位模板,不能直接使用。

关键文件: <WorkDir>\protk.dat（由 deploy\launcher\launch.ps1 物化）
3

Creo 用 LoadLibrary 加载 NativeHost.dll

By: 我们的代码(native)

这是我们的 C++ 插件。Windows 加载 dll 时会自动触发 DllMain——里面只做极简的启动日志(为了防御性诊断,一切写文件、不做复杂 IO)。

关键文件: src\CreoToolkit.NativeHost\src\host_entry.cpp
4

Creo 调 user_initialize()(主线程)

By: 我们的代码(native)

这是 Pro/Toolkit 规定的插件入口。我们在里面做四件事:

① 初始化 session 日志目录、retention、trace id 和 ETW；
② ctk_toolkit_touch() 验证当前 DLL 已由 Creo 正确注册并可调用 Toolkit；
③ 把当前 dll 路径写进环境变量 CTK_HOST_NATIVE_DLL(这一步很关键,为后面第 8 步做准备);
④ 校验 CTK_HOST_METHOD 后调用 invoke_managed()。模型预载已经移到 managed Diagnostics。

洞察: 到这里为止,一切都是 native C++ 的世界。.NET 还没进场。
5

经 mscoree 启动或附加 CLR 4（v4.0.30319）

By: 我们的代码(native)

NativeHost 调用 CLRCreateInstance → GetRuntime(v4.0.30319) → ICLRRuntimeHost::Start。进程里若已有 CLR 4 则附加，不 Stop()。 不加载 nethost.dll / hostfxr.dll。

部署铁律: 客户机需要 x64 .NET Framework 4.7.2+（Creo 4 年代 Windows 通常已带）。 不部署 nethost.dll。
6

ExecuteInDefaultAppDomain 加载 Host.dll

By: CLR 4

NativeHost 在默认 AppDomain 调用 CreoToolkit.Host.Bootstrap 的 public static int Method(string)（默认 InitializeApp）。 不需要 runtimeconfig.json。

从这一步开始,进程里同时有了 C++ 世界和 .NET Framework 世界。

7

调 Bootstrap.InitializeApp()——从 native 跨到 managed

By: 我们的代码(managed)

这是整条链路的转折点。控制权从 C++ 交给了 C#。InitializeApp 里做几件大事:

① CreoSession.Attach() 并校验 ABI；
② 可选运行 managed Diagnostics 的模型准备；
③ 在受限根目录中把 sample app LoadFrom 进默认 AppDomain（AssemblyResolve 共享 Host/Sdk/Interop）；
④ 注册命令/菜单,调用 ICreoApplication.OnInitialize；
⑤ 如设置 CTK_APP_RUN_COMMAND,再按名走与用户点击相同的 dispatch 路径。

关键文件: src\CreoToolkit.Host\Bootstrap.cs、CreoApplicationLoader.cs；src\CreoToolkit.App\CreoAppHost.cs
洞察: 这一步之后,插件就算"就绪"了,菜单已经在 Creo 里挂好,等待被点。
8

命令执行:managed 反向调 native,再进 Creo

By: 我们的代码(全链路)

用户点菜单(或环境变量自动触发)时,managed 命令实现会走这么一条路:

[DllImport("CreoToolkit.NativeHost")]  // 已由 Creo LoadLibrary 的同一 DLL
       ↓
NativeHost.dll 里的 Pro* / Ctk_* 转发
       ↓
Creo 真跑
洞察: 真正被加载的一直只有一个native dll: CreoToolkit.NativeHost.dll。P/Invoke 绑到这个已加载模块，不需要 sidecar 或 DllImportResolver。

§ 5 Deployment

05生产部署:每个 dll 住在哪

客户装机后,磁盘上文件的物理排布决定了上面每一步能不能顺利发生。

CreoToolkit 部署目录\ (可以是任意路径) start.bat / start-<app>.bat native\ CreoToolkit.NativeHost.dll ← 第 3 步 Creo 加载 protk.host.dat ← 无机器路径模板 managed\ CreoToolkit.Host.dll ← 第 6 步 ExecuteInDefaultAppDomain CreoToolkit.App.dll / Sdk.dll / Interop.dll / Diagnostics.dll / Polyfills.dll apps\<app-name>\ app.json ← type / assembly / msgFile CreoToolkit.Samples.ProtkAppls.*.dll CreoToolkit.Samples.PtDimension.dll ← module dll text\usascii\ protk_samples.txt ← 命令菜单文字资源 Creo 工作目录\ protk.dat ← launcher 从模板物化绝对 exec_file/text_dir logs\ ← 本次 session 的 native/managed 日志 Windows 系统\ .NET Framework 4.7.2+ (clr.dll v4.0.30319) ← 第 5 步 mscoree 启动/附加 用户目录回退\ %LOCALAPPDATA%\CreoToolkit\logs\host\ ← 未显式配置且 DLL 相对目录不可用时 <vendor>\dumps\ ← WER 崩溃转储
生产模式独有的关注: ① 客户机需 x64 .NET Framework 4.7.2+； ② native/managed dll 建议代码签名,防杀软误杀;③ 日志目录必须是普通用户可写目录：launcher 默认使用 <WorkDir>\logs，未显式配置时 NativeHost 才按 DLL 相对目录和 %LOCALAPPDATA% 回退。

§ 6 Fault modes

06每一步失败会怎样

下表是这条链路上曾经真实踩过、都留下疤痕的坑。看到症状时,直接对号入座。

步 症状 已知原因
3 Creo 报"无法加载 protk 应用" dll 依赖缺失 / 路径错 / 32-64 位不对
4 user_initialize 返回非零,Creo 报应用初始化失败 ctk_toolkit_touch 失败、text_dir 无效、managed entry 不在白名单或后续初始化失败；查 session JSONL
5 日志出现 CLR 启动失败 / ExecuteInDefaultAppDomain failed,插件初始化失败 客户机缺 x64 .NET Framework 4.7.2+，或 Host.dll 路径未解析到
6 整个 Creo hang 死 不要再拆第二颗 native sidecar 在 user_initialize 阶段调 Pro*；P/Invoke 必须打到已加载的 NativeHost
7 找不到 CreoToolkit.Host.dll CTK_HOST_ASSEMBLY 未设且 managed/ 相对 NativeHost 的布局不对
8 DllNotFoundException: CreoToolkit.NativeHost Creo 尚未 LoadLibrary NativeHost，或 PATH/SetDllDirectory 未指到 native 目录
这张表就是 P1 阶段几百个小时踩出来的伤疤。 现在链路能稳定跑起来的每一步背后,都对应着 memory 里的一条 lesson。

三种模式,一条链路,一份代码。 从 Creo 启动到我们插件命令就绪,系统里发生的 8 件事, 在开发/测试/生产三种场景下共享同一套注册和 dispatch 实现——变的是环境变量里的"纸条"要不要写字、 managed Diagnostics 是否准备模型、日志写到哪里、是否使用 GUI app。命令 Gate 能证明 handler 路径， 但不能替代真实 Creo 菜单/Ribbon、停止卸载和版本兼容性验收。
